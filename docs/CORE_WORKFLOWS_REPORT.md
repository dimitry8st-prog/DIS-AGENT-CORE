## Исправлено

- Проверка после ревью: компоненты резервного ключа `chat.id:message_id`
  валидируются до преобразования в строку. Небезопасные JS-числа отклоняются;
  большие строковые IDs различаются. Добавлен регрессионный тест.
- Исправлены все семь исходных Code-узлов: буквальные `\n` вне JS-литералов
  заменены настоящими переносами; строковые/regex escape-последовательности
  (`\d`, `\s`, newline внутри пользовательского текста) сохранены и проверены.
- Добавлен Webhook `webhookId`, корректные sub-workflow ссылки, passthrough
  контракта, ожидание результата и credentials только тестовой PostgreSQL-БД.
- Стабильные event IDs; Telegram ID передаётся строкой без потери точности;
  события без пригодного idempotency key отклоняются, а не получают новый
  случайный event ID при каждом повторе.
- Атомарная резервация с UNIQUE/PK, `duplicate`/`busy`/`previous_failed`;
  fencing владельца UUID защищает завершение и context lock. Только победитель
  проходит downstream и создаёт логи. Успех/ошибка и release lock транзакционны.
- Пользователь/контекст без строк не обрывают цепочку; неизвестный пользователь
  получает `registration_required`. TTL, active/busy/stale/inactive контекст,
  приоритет команд/callback и безопасный unknown route проверены.
- Ответы и прикладные логи используют allowlist. SQL-исключения очищаются
  внутри sub-workflows. Сохранение execution history/progress отключено.
- Additive миграция `002_core_processing.sql`, воспроизводимые автоматические
  тесты, mapping helper, README с импортом, проверкой и откатом.

## Оставшиеся ограничения

1. **Конфиденциальность внутренней БД n8n не подтверждена полностью.**
   `test_n8n_internal_soft_deleted_input_retention_limitation` ожидаемо падает:
   n8n 2.42.6 сохраняет исходный webhook input до исполнения WF-00, затем при
   `save=none` делает soft-delete. Физические данные остаются до штатного
   pruning. Сначала это была обычная падающая проверка; после диагностики
   assertion сохранён как отдельный expected failure. Проверки ответов,
   прикладных логов, console и доступной history проходят. Удаление прежних
   execution и изменение глобального pruning не выполнялись. Гарантия
   отсутствия секретов на диске требует отдельного решения до входа в n8n
   или изменения слоя хранения n8n; задача исправления пяти workflow это
   ограничение не устраняет.
2. **Отправитель webhook не проверяется.** Поиск Telegram ID — только lookup,
   не доказательство identity. Публичное/production использование не проверялось.
3. При полном отказе БД нельзя записать ошибку в неё: 503 может сопровождаться
   оставшейся резервацией `processing`. Повтор тогда возвращает `busy` даже
   после восстановления БД; необходима операторская сверка. Автоматический
   watchdog/retry/recovery следующих этапов не добавлен.
4. Payment/order/approval/LLM — только прежние значения router. Никаких внешних
   побочных действий и подтверждения оплат/прав доступа не реализовано.
5. Результаты относятся к текущей машине. Публикация облачной среды и
   восстановление в новой задаче сами по себе этими проверками не доказаны.

Рабочая цепочка первого этапа проверена функционально; полное соответствие
строгому требованию отсутствия секретов во внутреннем хранилище n8n не заявляется.
